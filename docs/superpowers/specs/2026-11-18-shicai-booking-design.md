## 1. 背景与目标

后勤处在校园内设有食材服务点，向全校教职工平价供应标准化包装食材（调料、粮油、干货、蛋类等，现有 66 个 SKU）。当前缺少线上预订渠道，教职工无法提前知道有什么、有多少，服务点备货也无依据。

本系统提供：

- **教职工端（企微内 H5）**：浏览商品 → 线上预订（商品、数量）→ 后勤备货 → 到点取货，现场支付
- **管理端（PC 网页，独立账号）**：商品维护、订单处理与备货、取货核销、统计对账

线上不涉及资金流（无线上支付），只做信息流（预订、备货、核销）。

## 2. 已确认的关键决策

| 决策点 | 结论 |
|---|---|
| 渠道 | 企业微信内嵌 H5（不做小程序） |
| 可见性 | 由企微应用**可见范围**控制为教职工，系统内不做身份白名单 |
| 认证（教职工） | 学校 CAS（已与企微打通），免注册免密码 |
| 认证（管理端） | 独立账号密码（不走 CAS），PC 宽屏界面 |
| 结算 | 取货现场支付（现金/扫码），线上不动钱 |
| 售卖模式 | 常规在售、无限购、下单后备货、随取 |
| 核销 | 6 位取货码 + 二维码，管理端扫码枪/手输核销 |
| 订单取消 | 待备货/待取货状态教职工可自行取消；管理员可代取消（填原因） |
| 技术栈 | Python 3.11 + FastAPI + SQLAlchemy 2.0 + MySQL 8；Vue3 + Vite + Pinia；H5 端 Vant，管理端 Element Plus |
| 部署 | 开发期本机 `http://10.204.0.146:13000`（CAS 已报备）；上线走 nginx 反代 + 校内正式域名 + HTTPS |

## 3. 总体架构

单体轻量架构，一个仓库、一个后端进程、一次部署。前后端以 REST API 分离，未来如需小程序可直接复用 API。

```
企业微信（可见范围=教职工）
   └─ 工作台入口 ──▶ H5
        ├─ /m      教职工端 SPA（Vant）
        └─ /admin  管理后台 SPA（Element Plus，PC 宽屏）
                   │
             FastAPI 单体（uvicorn）
        ├─ /api/auth/*        CAS 对接、教职工会话
        ├─ /api/products/*    商品浏览
        ├─ /api/orders/*      下单/取消/我的订单
        ├─ /api/admin/auth    管理员账号密码登录
        ├─ /api/admin/**      商品/订单/核销/统计/设置
        └─ /uploads           静态托管 Vue 构建产物与上传图片
                   │
                MySQL 8
```

## 4. 认证设计

### 4.1 教职工（CAS）

1. 企微打开 H5 → 前端检测无会话 → 302 至学校 CAS（`service` 为后端回调地址，**环境变量配置**）
2. CAS 与企微已打通，多数情况静默通过 → 带 ticket 回调 `/api/auth/cas/callback`
3. 后端调 CAS `serviceValidate` 校验 ticket，取得工号
4. 按工号 upsert 用户，签发 HttpOnly Cookie 会话（SameSite=Lax，HTTPS 下 Secure）
5. ticket 校验失败/过期 → 静默重跳 CAS（限制重定向次数防死循环）

**姓名获取（三层策略，目标是无感）**：

1. 联调时确认 CAS `serviceValidate` 是否释放姓名属性（`displayName`/`cn` 等）——有则直接用；没有可请 CAS 管理员为本服务配置释放属性（一次性）
2. 兜底：管理端「用户名单导入」（工号-姓名 Excel，人事处/工会现成名单），登录时按工号自动匹配
3. 最后兜底：匹配不上的首次登录补填一次姓名

CAS 对接封装为独立模块（`CASClient` 接口抽象），测试用 mock，不依赖真 CAS；上线前与学校 CAS 联调一次。

### 4.2 管理端（独立账号）

- 账号密码登录，bcrypt 哈希存储；同一工号失败 5 次锁定 10 分钟
- 首次部署通过环境变量初始化一个超级管理员
- 两档角色：**超级管理员**（全部权限 + 系统设置）、**操作员**（商品/订单/核销/统计，无系统设置）
- 管理员会话与教职工会话分离（不同 cookie/会话域）

## 5. 数据模型

| 表 | 关键字段 |
|---|---|
| `users` | 工号(唯一)、姓名、手机号(可空)、首次登录时间、最近登录时间 |
| `admins` | 用户名(唯一)、密码哈希、角色(super/operator)、姓名、状态(启用/停用)、最近登录 |
| `categories` | 名称、排序、启用 |
| `products` | 分类、名称、品牌、规格、单位、产地、原价、售价、图片URL、状态(在售/下架)、库存(**NULL=无限**；设数值则下单占用、取消回补)、排序、创建/更新时间 |
| `orders` | 订单号(如 `20261118-000123`)、用户、状态、商品总额、用户备注、6位取货码(随机数字，全局唯一，含历史订单)、各状态时间戳(下单/备货完成/取货/取消)、核销人、取消原因 |
| `order_items` | 订单、商品、**商品快照**(名称/规格/单位/单价)、数量、小计 |
| `admin_logs` | 操作人、时间、动作(核销/改价/取消/导出/登录等)、对象、详情摘要 |

设计要点：

- **商品快照**：订单项冻结下单时的名称/规格/单价，商品后续改价/下架不影响历史订单与对账
- **金额**：一律服务端计算，分（int）存储，不信任前端价格
- **库存**：无限购、多数商品不限库存（NULL）；个别限量商品（如柴鸡蛋到货 N 箱）可设数值，原子扣减防超卖（`UPDATE ... WHERE stock >= n`）

### 订单状态机

```
待备货(PENDING) ──管理员[备货完成]──▶ 待取货(READY) ──核销+现场收款──▶ 已完成(DONE)
     │                                    │
     └──────── 用户/管理员取消 ────────────┘▶ 已取消(CANCELLED)
```

- 仅 PENDING / READY 可取消或核销（条件更新，并发安全，后到操作返回明确错误）
- 不设自动过期（随取模式）；长期不取由管理员代取消
- 取消时有限库存自动回补

面向全校教职工（含临近退休的年长教师），界面大字、简洁、少层级。

| 页面 | 内容 |

| 模块 | 功能 |
|---|---|

| 商品管理 | 列表（搜索/分类筛选）；新增/编辑（名称、品牌、规格、单位、产地、原价、售价、图片上传、库存可空=无限、排序）；上架/下架；分类管理；**Excel 批量导入**（按现有 66 SKU 表格式做模板；按 名称+规格 匹配更新已有商品） |

## 8. 边界情况与错误处理

| 场景 | 处理 |
|---|---|
| CAS ticket 失效/校验失败 | 静默重跳 CAS，限制重定向次数防死循环 |
| CAS 带不出姓名 | 见 §4.1 三层策略 |
| 学生账号进入 | 不做系统内拦截；入口由企微可见范围控制 |
| 购物车商品已下架/改价 | 下单时服务端逐项校验，提示重新确认；价格以服务端为准 |
| 有限库存并发超卖 | 数据库原子扣减，失败明确提示库存不足 |
| 用户取消 vs 管理员核销并发 | 状态机条件更新，后到操作返回明确错误 |
| 重复核销 / 核销已取消订单 | 红字拦截并显示订单当前状态 |
| 图片上传 | 限 jpg/png/webp、≤5MB，存 `/uploads`，路径入库 |
| Excel 导入错误 | 逐行校验，报告"第 N 行第 X 列：原因"，事务式部分成功策略（正确行导入，错误行报告） |
| 接口安全 | admin 接口校验管理员会话；用户只能查/操作自己的订单；参数化查询；下单按用户限流 |
| 长期不取订单 | 管理员代取消 |

## 9. 安全清单

- 密码 bcrypt 哈希；管理员登录失败 5 次锁 10 分钟
- HttpOnly + SameSite cookie，HTTPS 下 Secure
- 所有 SQL 走 ORM/参数化；前端 Vue 默认转义（公告等富文本如引入需白名单过滤）
- 上传文件类型与大小校验
- 环境变量管理密钥（CAS 地址、DB 口令、初始超管），不入库不入 git

## 10. 测试策略

- **后端 pytest**：单元（订单状态机、库存扣减/回补、金额按分计算）；接口（TestClient + mock CASClient：登录、下单、取消、备货、核销全流程）
- **E2E（Playwright）**：登录 → 加购 → 下单 → 备货完成 → 核销 主链路
- **CAS**：接口抽象 + mock，测试不依赖真 CAS；上线前真环境联调一次
- 覆盖率目标 ≥80%
